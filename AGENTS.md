# Repository Instructions

## Repository shape

- This is a single-package TypeScript ESM OpenCode plugin. `src/index.ts` is the public runtime entry and must expose only the default `PluginModule`; package and runtime smokes enforce that export shape.
- The execution path is: plugin options parsed in `src/config/` -> named connection selection in `src/connections/` -> tool definitions in `src/tools/` -> OpenAI Images transport in `src/protocol/openai-images/` plus local/remote asset handling in `src/files/`.
- `dist/` is generated by `tsc`, ignored by Git, and must not be edited manually. With `NodeNext`, relative TypeScript imports keep their `.js` suffixes.
- Dependencies use `package-lock.json` and `npm ci`; tests use Bun. There is no repository lint or formatter script.

## Commands and focused verification

- `npm run typecheck` checks types without emitting files.
- `npm run build` cleans and rebuilds `dist/`.
- `bun test` runs the full suite; run one file with, for example, `bun test test/config.test.ts`.
- `npm run verify` runs typecheck, clean build, all tests, package-content checks, and the compiled-plugin smoke. It does **not** run either real-OpenCode smoke.
- `npm run check:package` requires a built `dist/` and must be invoked through the npm script; calling `node scripts/check-package.mjs` directly is intentionally rejected.
- `npm run smoke:opencode` starts a clean real OpenCode process and verifies plugin discovery, tool registration, and host-side `{env:...}` / `{file:...}` interpolation without contacting an external Images service.
- `npm run smoke:runtime` is Linux-only. It drives both tools through a real OpenCode session using loopback fake relays, so it is deterministic and no-cost. Both OpenCode smokes use `OPENCODE_BIN` when set, otherwise `opencode` from `PATH`.
- For release-oriented changes, follow the ordered checks and isolate-install procedure in `docs/release.md`; `npm run prepublishOnly` validates but never publishes.

## Plugin contract

- The public abstraction is a map of named image `connections`. These are separate from OpenCode model providers and are never inherited from provider configuration.
- Treat each connection `baseURL` as the exact API root. The transport appends `/images/generations` or `/images/edits`; it must not guess or inject `/v1`.
- OpenCode expands `{env:NAME}` and `{file:path}` before plugin options arrive. Do not add a second interpolation or secret-loading layer inside this plugin.
- `outputDir`, tool `out` values, edit inputs, and masks are workspace-relative by design. Do not accept absolute paths or `..`; use the intended workspace root instead.
- Keep public behavior provider-neutral: no provider-specific URL, model, authentication branch, or private relay detail in source, tests, fixtures, or documentation.
- The current Images transport is non-streaming and sends `n=1`. Generation and edit protocol details, including multipart behavior, are contract-tested; update tests and compatibility docs with any intentional change.
- When changing the supported OpenCode range, update `engines`, peer/dev dependencies, CI installation, smoke assertions, and compatibility documentation together.

## Security invariants

- Preserve the `src/files/` containment model: canonical workspace checks, symlink safety, bounded reads, image magic-byte inspection, and atomic non-overwriting output writes. Symlink and hard-link safety tests are mandatory in CI.
- Do not add automatic retries around image generation or edit POST requests; a retry can duplicate a billed operation.
- Error paths must continue redacting the configured API root, credentials, and custom header values. Do not include raw upstream bodies or configuration dumps in errors or logs.
- Do not weaken restricted remote-asset fetching, response-size limits, forbidden-header validation, or workspace-relative output rules without corresponding security tests and documentation.
- Automated tests and smokes must use injected fetches or loopback fake services. Any external, quota-consuming, or paid Images request requires explicit human approval and must never become a default test path.

## Packaging and release gates

- `package.json#files` intentionally ships compiled output, public docs, and governance files while excluding source, tests, scripts, lockfiles, local notes, and secret-like files. Keep `scripts/check-package.mjs` aligned with any deliberate package-content change.
- GitHub workflows verify candidates only; they do not publish to npm or create a GitHub Release. Commit, push, tag, GitHub Release, and npm publication are separate human-approved actions described in `docs/release.md`.
- Never place credentials, private endpoints, personal accounts, machine-specific absolute paths, generated test images, or private-provider artifacts in committed files. Use repository-relative paths, environment-variable names, and obvious placeholders only.
