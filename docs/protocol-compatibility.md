# Protocol compatibility

The local transport targets the standard OpenAI Images request boundary without binding the plugin to a particular provider, URL, model, or relay brand.

## Endpoints

The configured `baseURL` is used exactly after removing trailing slashes:

- `POST <baseURL>/images/generations`
- `POST <baseURL>/images/edits`

The plugin does not add `/v1`, remove an existing path prefix, or discover a provider-specific route. Configure the complete API root explicitly.

## Generation request

Generation uses `application/json` with:

```json
{
  "model": "configured-model",
  "prompt": "...",
  "n": 1,
  "size": "optional",
  "quality": "optional",
  "background": "auto",
  "output_format": "png",
  "output_compression": 80,
  "moderation": "auto"
}
```

Only fields that have a value are sent. `n` is always `1`; the plugin does not expose a user-controlled batch count or streaming mode.

## Edit request

Edits use `multipart/form-data` generated by the runtime. The form contains:

- `model`
- `prompt`
- `n=1`
- Optional `size`, `quality`, `background`, `output_format`, `output_compression`, `moderation`, and `input_fidelity`
- One `image[]` file part per prepared input image, in caller order
- One optional `mask` file part

Local paths are prepared by the file layer first. The transport receives binary bytes, a filename, and a MIME type; it does not read paths itself. The edit tool accepts 1–16 images, and a mask is associated with the first input by tool policy.

## Authentication and headers

`apiKey` becomes a Bearer authorization header. Custom headers are merged with the request headers after configuration validation. `apiKey` and `headers.Authorization` cannot both be configured. JSON requests receive `Content-Type: application/json`; multipart requests leave the boundary to the runtime.

## Response normalization

Successful JSON responses must contain a non-empty `data` array. Each item must contain exactly one supported image form:

- `b64_json`: normalized as a base64 asset.
- `url`: normalized as a URL asset.
- `data_url`: normalized as a data URL asset.

An optional `revised_prompt` is retained in tool metadata. Remote result materialization then applies the local file policy: decoded assets are limited to 50 MiB, data URLs require canonical padded standard base64, and URL downloads require HTTPS and the restricted host policy described in [Security](security.md). Actual image magic determines MIME and dimensions rather than trusting a declared content type or extension.

The transport accepts HTTP and HTTPS URL syntax while normalizing the provider response; the file layer intentionally permits only HTTPS for downloads.

## Lifecycle and retry semantics

Requests are non-streaming and use `n=1`. Caller cancellation and the configured timeout cover the request and response-body read. POST requests are not automatically retried. This avoids silently repeating a potentially billed generation or edit.

Multiple response assets may be materialized sequentially by the tool chain, but this does not change the outgoing `n=1` request contract.

## Compatibility expectations

The implementation supports common OpenAI Images-compatible extensions such as custom bounded `size` and `quality` strings, `background`, `output_format`, `output_compression`, `moderation`, and edit `input_fidelity`. A relay may still reject any of these fields, or may implement only generation or only edits; configure its capability flags accordingly.

“OpenAI-compatible” is not a universal compatibility promise. Before selecting a relay, verify its exact Images endpoints, authentication behavior, model identifier, multipart field names, supported parameters, response asset form, and output limits.
